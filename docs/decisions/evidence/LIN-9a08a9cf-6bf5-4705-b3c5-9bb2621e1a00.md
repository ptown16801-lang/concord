**Canonical operating rule:** This document controls whenever its guidance conflicts with any Concord workflow, migration, or historical document.

This rule governs Concord project execution, delegation, reopening, and workload creation.

## Mandatory preflight before any project action

Before creating, assigning, restarting, executing, delegating, reopening, or modifying any project workload:

 1. **Check the current authoritative state first.**
    * Review the latest project decisions.
    * Review completion, cancellation, and supersession history.
    * Check whether the requested work already exists or has already been completed.
    * Check the current repository/artifacts when relevant.
    * Do not infer that an open Linear issue means unfinished work.
 2. **Latest explicit owner decision wins.**
    Historical issue descriptions, old prompts, previous execution instructions, and stale Linear states must never override a later explicit owner decision.
 3. **Completed means completed.**
    If a project or deliverable has been declared complete, deployable, accepted, or removed from pending work, do not restart or recreate it unless the owner explicitly reopens it or a specific verified defect requires work.
 4. **“Execute X” means execute the currently valid remaining work for X.**
    It does not mean replay old workloads, reopen canceled issues, rebuild completed deliverables, or repeat already-finished work.
 5. **Audit before dispatch.**
    Before assigning any agent or workload, establish:
    * current project state,
    * what remains unfinished,
    * what is already complete,
    * the exact work about to be dispatched.
      If there is no verified unfinished work, do not dispatch anything.
 6. **Linear is coordination only unless explicitly authorized otherwise.**
    Use Linear for planning, issue tracking, dependencies, status, supervision, and evidence.
    Do not use Linear coding agents, coding sessions, or implementation delegation unless the owner explicitly asks for Linear to perform coding.
 7. **Do not create duplicate work.**
    Search existing issues, artifacts, branches, PRs, and completed deliverables before creating new work.
 8. **Do not convert assumptions into decisions.**
    If an assumption is required, state it explicitly to the owner before acting.
 9. **Do not reopen settled questions.**
    Reuse prior answers and decisions. Ask only when a genuinely new unresolved product decision blocks progress.
10. **When state conflicts exist, resolve the state before dispatch.**
    Identify the latest authoritative decision and continue from that state. Do not blindly reactivate historical instructions.

## Finger-specific standing rules

* **Finger deployable beta is complete. It is not pending work.**
* Only verified residual defects or explicitly requested new features may create new Finger implementation work.
* **Never use Linear to code Finger unless the owner explicitly asks to use Linear's coding agent.**
