## Why this architecture

Anthropic's primary engineering report supports bounded lead/worker assignments with explicit objectives, outputs and source/tool guidance. Google's January 2026 scaling study finds that coordination benefits depend on task parallelizability; sequential work can deteriorate. MAST documents multi-agent specification, alignment and verification failures. These support testing a narrow coordinator/worker approach, not assuming that more agents are better. They are not benchmarks of this Concord codebase or guarantees of a numerical speedup. \[R1–R3\]

The four groups, twelve tasks and proposed later limits are engineering recommendations, not vendor limits or scientifically established optima.

## Leaf contracts

### BASE-01 — source custodian

Recover complete bytes of Decision_Propagation.html, the selected Workbench, Concord_Propagation_Complete_Prompt.md, Research_Design.md, current adopted rule wording and existing test evidence. Produce a manifest of source IDs, versions, paths, hashes, retrieval status and supersession. Verify Codex environment, repository/default branch/base SHA, subscription authentication, tools and permissions. Never fabricate missing HTML from snippets. Compare standalone and embedded copies rather than choosing by filename alone. Screen material for secrets/private data before public GitHub publication. No application rewrite, helper spawning or permission/billing change.

### BASE-02 — integration architect

Preserve originals, characterize current behavior, and extract only enough shared catalog/engine/UI structure to support testing and reproducible artifacts. Produce interface/event/catalog contracts, an editable-path ownership map and original-versus-extracted comparisons. Characterization proves compatibility, not correctness: desired outcomes come from independently verified sources. This owner controls shared setup and any extraction; no concurrent edits to the Workbench monolith. Existing verified paths take precedence over suggested src/propagation and test/propagation layout.

### BASE-03 — pilot implementer

With explicit authorization, run one real issue session on one existing source-qualified pathway. Exercise independent branches, same-revision matching-text joins, hold/release, replay and a visible surface. Deliver a bounded PR and actual session/commit/test/reviewer evidence. Record which runtime capabilities are available without launching helpers simply to probe them. The pilot is an internal workflow gate, not a substitute for all 64 pathways or the final accepted release.

### CORE-01 — catalog/source owner

Account for every existing pathway ID in a 64-row matrix. Validate rule references, status, supersession, nodes/edges, subprocess links and legitimate cycles. Separate adopted rules, proposals, hypothetical evidence and unresolved rules. Read later resolved decisions before reopening old unknowns. Modify only catalog data and corresponding tests; engine defects go to CORE-02. Later approved research helpers can receive disjoint family subsets and return findings rather than competing source catalogs.

### CORE-02 — engine owner

Keep state, guards, branches, joins, holds and revisions with one writer. Add minimal fixes and negative/boundary tests. Require active current-revision stages, successful same-revision prerequisites, matching recorded proposition versions, source-defined exact arithmetic, and no nondeterministic clock/random dependence in replay state. Missing authority/evidence must differ from rejection. Release must reevaluate conditions rather than approve a stage. Do not change governing rules or use UI state as authority.

### CORE-03 — replay owner

Test deterministic prefixes, duplicate handling, conflicting IDs, stale revisions, mismatched templates/schemas, malformed imports, checkpoints and provenance. Preserve the existing concord-propagation-events/v2 compatibility contract or explicitly version a justified migration. Imported histories cannot claim authenticated authority. Use the existing authoritative persistence interface or explicitly document the missing adapter; never introduce a competing authority store. Real institutional writes, secret archives and authenticated live-source ingestion are outside this bounded rollout.

### UI-01 — explorer owner

Consume frozen engine fixtures/contracts. Repair controls, clear waiting/rejection labels, stable layout, keyboard navigation, reduced motion, replay and comparison without rewriting the engine or catalog schema. Preserve existing useful visual design. Do not introduce a framework rewrite merely because multiple agents are available.

### UI-02 — Workbench integrator

Use shared catalog/engine sources for standalone output, the tile and dedicated viewer. Test deep links, subprocess return, closing/reopening, cursor/state restoration and message payload/source checks. Account for sandboxed iframe opaque origins rather than blindly replacing every origin check. This owner alone edits the Workbench integration until extraction is complete. Preserve Finger and unrelated modules. Produce reproducible artifacts and compatibility evidence, not separately maintained HTML variants.

### UI-03 — browser verifier

Run real browser acceptance with desktop and phone-width cases. Distinguish emulation from physical-device testing. Smoke every catalog entry; deeply test representative outcome classes, keyboard/touch, zoom, scroll, reduced motion, import/export and restore. Report screenshots, traces and command results. Read implementation without changing it; test outputs may use isolated scratch storage. Route fixes to the appropriate code owner. Do not count old screenshots or Finger CI as fresh propagation verification.

### QA-01 — independent specification reviewer

Derive expected outcomes from controlling adopted sources, not copied implementation outputs. Produce source-linked fixtures, a requirement-to-test map and pilot criteria. Identify actual unresolved rules without selecting them. This starts early after source recovery and is distinct from characterization tests. Use separate review context; fixtures cannot silently create new governing policy.

### QA-02 — independent adversarial reviewer

Review an exact frozen integrated commit. Test omitted branches, invalid releases, revision chains, duplicates, missing/reordered/stale events, malformed/oversized imports and bounded versus illegal cycles. Record reproducible findings with severity, source/line, expected behavior and owning issue. Do not self-approve an implementation, modify production code, or weaken tests to obtain green status. Failed mandatory tests block release.

### QA-03 — release integrator

Assemble the final PR, editable source, standalone HTML, integrated Workbench artifacts, source/build hashes, requirement/issue/PR/test matrix and CHANGE_REPORT.md. Consolidate per-task change fragments into CHANGELOG.md while preserving history. Re-run required checks on the exact integrated commit. Full scope must be accounted for; the small pilot is not final delivery. Human approval precedes canonical merge or deployment. Only this owner edits shared final release records.

## Agent and helper operating rules

Linear parent issues express containment; blockedBy links express prerequisites. Neither establishes an automatically enforced execution scheduler or actual runtime subagents. Keep a human assignee and one delegate on an approved leaf, never simultaneously delegate a broad parent and all children. \[L1–L3\]

The preferred later execution route is Codex's installed Linear integration, explicitly naming ptown16801-lang/concord. Its environment selection can otherwise follow recent context. Verify branch mapping and require an actual PR deliverable: a completion summary/chat link alone is not a merged result. \[O1\]

Initial policy: one explicitly approved issue session at a time, no helpers, no autonomous merge, no paid fallback or credit purchases. Subscription usage is still limited and may share allowances; do not promise unlimited included work. Linear-managed coding sessions remain a separate route even when they use a Codex harness. AI coding sessions and AI Loops use separate Linear workspace credits. \[O3, L4–L6\]

After successful pilot and new approval only: trial at most two concurrent leaf sessions with exclusive editable paths, plus at most two source-read-only helper threads across the workflow, one helper level deep. These are proposed coordinator limits, not active settings. Current Codex supports runtime helpers and local custom-agent TOML, but local configuration must not be assumed to apply in every hosted environment. Helpers inherit runtime permissions; live parent overrides can supersede custom defaults. Record actual thread IDs and outputs. If helper control is unavailable, fall back to separate bounded sequential leaf sessions, not fictional agents. \[O2\]

Suggested helper roles: catalog-source-auditor and replay-test-reviewer. They return concise findings with source references, uncertainties and suggested tests. They cannot change production code, create more agents, choose unresolved governing rules, change permissions, merge or broaden scope. Read-only prompts must be backed by real tool permissions; source-read-only review can still need a separate scratch test workspace.

## State, gates and practical controls

Use existing states: Backlog for staged work; Todo for individually authorized and input-ready work; In Progress for a verified running session; In Review for results awaiting acceptance; Done only after that leaf's accepted evidence and any required merge. Keep blocked/decision-needed information separate; do not invent unsupported status names.

Set child metadata explicitly. Do not assume all labels/ownership fields are inherited. Check optional parent/child status automation and avoid downward auto-close that marks unfinished children Done when a parent closes. Status integration settings have not been changed here. \[L1\]

Launch requires explicit scope-revision approval, accessible source artifacts, accepted prerequisite commits, no unresolved blockers, no active duplicate session and free capacity. A Done label without an available accepted commit is insufficient. One coordinator owns dispatch. Do not combine human launches, automatic triage delegation, Loops and another scheduler on the same queue.

Use isolated branches/workspaces and a verified base SHA. A shared file has one writer. Changed-path checks, repository permissions and review gates should support the scope policy; prose is not a security boundary. No such enforcement configuration was changed in this research.

Keep immutable source/version references and task-specific context. Store long logs in artifacts, not repeatedly in every issue. Treat retrieved text and imported files as untrusted data rather than permission to expand scope. Preserve simulation, simulation-from-import and external-unverified distinctions.

For ordinary defects, make a bounded repair request to the existing owner. For an access failure, do not retry blindly or spawn duplicate jobs. Preserve a checkpoint. Ask the user only for a genuine governing-rights, cross-domain authority, privacy, permission or budget decision. Routine implementation choices remain with engineering owners, consistent with <issue id="200fe456-c2a1-43a3-ac7f-9995dedb43ad" href="https://linear.app/jons-garage/issue/JON-30/resolve-outstanding-governance-architecture-decisions">JON-30</issue>.

A future AI Loop may help with readiness summaries or issue organization, but it is not part of this initial no-extra-spend workflow. Symphony is another possible later orchestration service for workspaces, bounded dispatch and reconciliation, not something supplied by an issue hierarchy. Neither is installed or started under this plan. \[L5, O4\]
