## Proposed changes

### 1. Verify the actual published runtime

Inspect the existing canonical Loop by UUID in native Linear, resolve the conflicting historical URL without creating/reactivating anything, compare published content with the current canonical policy revisions, and read the latest successful run and action receipts. Record unknowns honestly. On adoption, replace the affected canonical paragraphs, publish that same Loop, and run one bounded validation. A document edit alone cannot count as deployment. Preserve existing permissions and hourly America/New_York cadence.

### 2. Give every actionable review a next owner and action

Use the existing task contract, not a new mandatory schema:

`artifact/revision | reviewer or correction owner | verdict/open findings | next action | blocker/release evidence`

* Missing artifact: Todo for completion of the existing assignment, with a specific local blocker when present.
* Delivered, unreviewed: In Review with one bounded acceptance review.
* Changes required: Todo for correction of the existing artifact; reflect In Progress only on actual execution evidence; recheck affected findings after delivery.
* Passed: Done only when the current revision satisfies the existing acceptance authority and any required owner approval.
* Explicitly deferred: retain honest lifecycle state and evidence; exclude from the actionable queue.

J remains accountable, but routine conformance review should use the existing authorized reviewer path, not silently become a fresh owner-approval gate. New owner decisions and permissions remain reserved.

### 3. Allocate free capacity to completion first

Prioritize urgent missing deliveries/corrections, then their reviews and feedback integration, then newly eligible coin-model children. Preserve useful active workers and independent parallel work. Reuse <issue id="102d289a-aa72-49e9-b8e5-916cebcdd1e8" href="https://linear.app/jons-garage/issue/JON-97/coin-model-a-formal-specification-and-interview-audit">JON-97</issue> and <issue id="1e1d4d62-b365-4e39-9383-fb51bbe3d760" href="https://linear.app/jons-garage/issue/JON-106/coin-model-j-prior-art-replication-and-source-verification">JON-106</issue> first where currently ready and ownership/capabilities permit; do not create replacement tasks. <issue id="c0338f48-02fd-428e-9751-8b4a7b2d4a34" href="https://linear.app/jons-garage/issue/JON-99/coin-model-c-threat-and-emergence-model">JON-99</issue>/<issue id="bac88603-09ee-44cf-b938-4d0f833c6ade" href="https://linear.app/jons-garage/issue/JON-100/coin-model-d-hidden-research-instrumentation-contract">JON-100</issue> reuse existing drafts and findings; <issue id="454fb972-eb24-4af9-be23-eea326b44450" href="https://linear.app/jons-garage/issue/JON-101/coin-model-e-minimal-agent-facing-interface-contract">JON-101</issue>/<issue id="cdc37030-0e94-48f8-9c96-f8fea0105eb7" href="https://linear.app/jons-garage/issue/JON-102/coin-model-f-concord-integration-plan">JON-102</issue> advance only when their actual next-phase inputs are satisfied. Other independent design can continue when no eligible urgent action is available.

Use one continuation/delegation path per deliverable. A delegate field, old launch receipt, or stale session does not prove a worker is active or that a replacement is safe. Do not enable coding, external connectors, or a new delivery route merely to repair a design handoff.

### 4. Distinguish draft availability from acceptance

Qualify each relevant dependency by the next action: drafting, review, acceptance, or implementation. Reviewing an artifact requires that artifact to exist, not that it already passed the review. Using a permitted draft is not acceptance. Preserve real blockers and frozen decisions; do not delete dependencies merely to fill worker slots. Keep this qualification in existing task contracts, not a second dependency engine.

### 5. Separate no-op, first dispatch, and retry

An already-satisfied tracking state needs no write. A ready, already-authorized action with no attempt and no live/recoverable owner may still receive its first execution even when its issue is unchanged. Retain these pending actions in the existing checkpoint alongside changed issues, so incremental scans do not lose older ready work.

Preserve the numerical ceiling of three, but count actual unsuccessful action attempts—not scans or waiting observations. Suggested checkpoint key: `canonical issue + condition + intended action + relevant input revision`. Own bookkeeping or cosmetic revisions do not reset failure accounting. Material new evidence can release the relevant condition; repeated failure to correct the same finding is still no progress.

A bookkeeping key is not an API exactly-once guarantee. Reconcile ambiguous launch responses against native receipts before retrying. Unknown ownership blocks that action, not the whole project. After the ceiling, retain one blocker/release condition and stop repeated notifications or retries.

### 6. Make closeout recoverable, not falsely atomic

Read actual output and acceptance; update the issue and existing run checkpoint; read back the result. If a tracking write fails after successful delivery, retry the missing tracking step, not the worker. Do not promise a cross-system transaction spanning Linear, GitHub and run history. Verify that native checkpoint persistence actually works; do not quietly create a competing external store.

## Proposed replacement paragraph

> Separate bookkeeping, first execution, and retry. A matching tracking state requires no write; it does not cancel a ready, already-authorized action that has never been attempted. Read changed evidence plus known pending actions and affected dependencies. For each, record the artifact revision, actual disposition, responsible next actor, and specific release condition. Recover existing work before any new launch. Prioritize urgent missing deliveries, corrections and acceptance reviews, then eligible downstream work, within existing permissions and non-overlapping capacity. Reuse existing review reports. A completed reviewer task is not producer acceptance. Count only actual unsuccessful action attempts toward the existing three-attempt ceiling; do not count scans, waiting, or self-authored bookkeeping. Do not reset failure accounting for cosmetic changes. Resolve ambiguous dispatch outcomes from native receipts before another attempt. After a worker stops, reconcile delivery, acceptance and tracking together; read back changes and preserve incomplete closeout steps without rerunning delivered work. Keep explicit holds out of the actionable queue, not falsely Done. End unchanged paths quietly.

Essential boundaries remain once in effective context; links are not loaded context. This proposal does not claim control over hidden prompts, caching or billed token savings.
