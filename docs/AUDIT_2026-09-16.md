# Vote / Concord project audit — 2026-09-16

## Scope

This audit reconciles the currently accessible **Vote / Concord** project records with the GitHub repository `ptown16801-lang/concord`, concentrating on the deployable Finger beta because that is the code currently present in this repository.

Reviewed evidence included:

- the repository default branch and all three Finger implementation branches that existed at audit start;
- open/merged Finger pull requests and their diffs;
- the full current repository tree, source files, SQL migration, tests, package metadata, and CI workflow;
- the project File Library's recent Workbench and decision-record variants;
- the `Vote Research Library — Archiver and Identity Audit` workbook's `Current Status` sheet; and
- historical conflict/status records only as provenance, not as proof of current implementation state.

This audit does not claim that every external byte in the wider Vote archive is present in this GitHub repository. The purpose is to establish a consistent current code baseline and an explicit ordering for the broader records that were accessible.

## High-level result

No project-blocking conflict requiring a user decision was found.

The main issue was **divergent implementation history**, not irreconcilable requirements: the repository default branch already contained the stronger merged Finger persistence/identity implementation, while two draft branches independently added an end-to-end browser implementation and replay/heat-map processing. Blindly merging either draft would have reintroduced a second storage authority and weaker identity/access assumptions.

The audit therefore used the merged persistence branch as the base, selectively incorporated compatible work, hardened the resulting runtime, and added canonical reconciliation records.

## Findings and repairs

### A-01 — competing backend/storage implementations

**Finding:** The end-to-end draft branch introduced its own server, SQLite store, artifact layout, analysis implementation, and admin routes after a different persistence architecture had already been merged.

**Risk:** Two competing definitions of authoritative Finger storage and analysis would make retention, identity, purge, and downstream references inconsistent.

**Repair:** Retained the merged `FingerSqliteRepository` + `FileObjectStore` + `FingerPersistence` + `PersistentFingerStore` stack as the single canonical backend. The temporary duplicate runtime-store staged during reconciliation was deleted once this was confirmed.

**Status:** fixed.

### A-02 — caller-controlled filesystem path in simple store

**Finding:** The simple `FileFingerStore` constructed a session directory directly from `session.id`.

**Risk:** A direct caller could supply path-like input and cause storage outside the intended session directory.

**Repair:** The logical session ID is retained in metadata, while the physical directory name is now `SHA-256(session.id)`. Directory/file permissions were tightened and a regression test uses `../../escape-attempt` to verify the store remains within its configured root.

**Status:** fixed and regression-tested.

### A-03 — divergent artifact path construction

**Finding:** The end-to-end draft store also used a caller-controlled session ID inside artifact filesystem paths.

**Repair:** That storage implementation was not adopted. The canonical `FileObjectStore` accepts only strict content-addressed keys of the form `finger/sha256/<prefix>/<sha256>`, verifies path containment, and now creates object-store directories with mode `0700` and files with mode `0600`.

**Status:** fixed by canonicalization/hardening.

### A-04 — administrative-read authentication mismatch in draft server

**Finding:** The draft end-to-end server's admin guard treated an unset admin token as allowing access even though its README described the token as protecting administrative read routes.

**Risk:** History/artifact/comparison routes could be exposed without authentication in a deployment that omitted the token.

**Repair:** Those divergent public admin routes were not merged. The reconciled server exposes only health, browser config, ingestion, and static beta files. History/artifact/comparison/purge operations remain internal storage/library functions pending an explicit authenticated administrative surface.

**Status:** fixed by not adopting the inconsistent route layer.

### A-05 — client-controlled authenticated identity in draft server

**Finding:** The end-to-end draft treated `x-concord-user` and some body identifiers as trusted identity by default.

**Risk:** A directly reachable endpoint could associate captures with an arbitrary claimed Concord user.

**Repair:** Retained the merged signed HttpOnly anonymous identity cookie. Authenticated `x-concord-user` trust is opt-in only with `FINGER_TRUST_CONCORD_USER_HEADER=true` and is documented as requiring a protected upstream boundary that strips direct client values.

**Status:** fixed.

### A-06 — duplicate persistent browser association ID

**Finding:** The initial collector reconciliation retained a separate `localStorage` association ID even though the server already supplies a stable signed identity cookie.

**Risk:** Redundant persistent browser identifier and competing association semantics.

**Repair:** Removed the persistent localStorage association identifier. Server-signed identity is the longitudinal association authority; the collector keeps only a session-scoped visit ID plus server-generated capture identity.

**Status:** fixed.

### A-07 — sensitive editable content in DOM/key capture

**Finding:** Raw DOM snapshots and mutation nodes could include editable/form content, and keyboard events recorded `event.key` characters.

**Risk:** Unnecessary retention of typed or rendered sensitive values.

**Repair:** DOM snapshots/mutation node serialization now redact `input`, `textarea`, `select`, `contenteditable`, and explicitly marked `[data-finger-redact]` content. Keyboard records keep structural key metadata such as `code`, location, repeat, and modifiers but not the literal `event.key` value. The general warning remains that DOM/behavioral capture is sensitive and deployments should minimize further according to their environment.

**Status:** fixed/minimized; deployment-specific privacy review still required.

### A-08 — collector timing lost during durable normalization

**Finding:** Canonical persistent ingestion looked for numeric `timeStamp`/`timestamp`; the browser collector writes an ISO `timestamp` plus capture-relative `elapsedMs`. As a result the stored `occurred_at_ms` could fall back to the event sequence rather than the real capture-relative time.

**Repair:** Normalization now prioritizes `elapsedMs`, then other numeric timing fields, and can parse an ISO timestamp as a final fallback. Pointer kind is also inferred from touch/mouse event names when no explicit `pointerType` exists.

**Status:** fixed with dedicated regression coverage.

### A-09 — replay processor timestamp/viewport mismatch

**Finding:** The replay branch expected timestamp forms that did not fully match the reconciled collector and primarily expected a top-level viewport.

**Repair:** Processing now prefers collector-relative `elapsedMs` anchored to `startedAt` and can use per-event viewport dimensions when top-level viewport data is unavailable.

**Status:** fixed with regression coverage.

### A-10 — CI branch mismatch

**Finding:** Draft CI configuration was tied to a `main` branch that was not the repository's current default branch.

**Repair:** Added a branch-safe workflow triggered by pushes and pull requests, running syntax checks and the Node test suite on Node 22 and Node 24.

**Status:** fixed.

### A-11 — runtime/config duplication

**Finding:** During reconciliation an extra configuration module and a duplicate runtime store briefly existed alongside the canonical backend.

**Repair:** Both duplicate paths were removed. Runtime configuration is parsed once in the server entry point; storage authority remains singular.

**Status:** fixed.

### A-12 — custom storage-path startup inconsistency

**Finding:** Custom database paths could point to a parent directory that did not exist, and a custom object directory could be relative even though `FileObjectStore` requires an absolute root.

**Repair:** Database and object-store paths are resolved before construction and their directories are created at startup. Capture timing/body/port bounds are validated once at startup rather than during individual requests.

**Status:** fixed.

### A-13 — fragmented project/change records

**Finding:** The broader archive contains repeated decision snapshots and specialized later variants; GitHub branch/PR descriptions also carried overlapping Finger change histories.

**Repair:** Added:

- `CHANGELOG.md` — consolidated implementation history;
- `PROJECT_RECORD.md` — project identity, source precedence, decision-file reconciliation, Workbench/Research-Library status, and branch reconciliation; and
- this audit report.

Older artifacts are preserved as provenance rather than deleted.

**Status:** reconciled.

## Known remaining engineering gaps

These are not contradictions requiring a project decision, but they remain real work outside this cleanup:

1. **Browser-level interaction tests.** Current CI covers syntax and Node tests; it does not yet run Playwright/WebDriver tests of focus, touch/pointer behavior, DOM redaction, responsive layout, or admission navigation in a real browser.
2. **Authenticated administrative UI/API.** Storage/history/purge capabilities exist internally, but a production administrative surface still needs explicit authentication/authorization, rate limits, audit policy, and least-privilege design.
3. **Automated derived-analysis persistence.** Replay/heat-map processing is available as a library; the canonical raw persistence remains authoritative. Automatic analysis-generation scheduling should be added only through the existing append-only generation/persistence interface, not through another store.
4. **Operational secret/backup policy.** `FINGER_IDENTITY_SECRET`, database/object-store backup, retention, restore testing, and key rotation are deployment responsibilities not proven by this repository alone.
5. **External archive canonicalization.** GitHub now has a project-record index, but the wider File Library still contains historical duplicates by design. A future archive UI/index could point to canonical successors without deleting provenance.
